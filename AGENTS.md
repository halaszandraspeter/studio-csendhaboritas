# Agent guide — csendhaboritas Sanity Blueprint + Studio

Read this before touching this repo. It captures non-obvious layout rules and
gotchas that are easy to get wrong.

## Repository layout (simple monorepo)

```
studio-csendhaboritas/            ← repo root = BLUEPRINT project
├─ sanity.blueprint.ts            ← Blueprint manifest (deploy from HERE)
├─ .sanity/blueprint.config.json  ← local stack binding (gitignored)
├─ functions/
│  └─ vercel-deploy/index.ts      ← Sanity Function (triggers revalidate + Vercel)
├─ package.json                   ← ONLY blueprint + function deps
├─ tsconfig.json                  ← for blueprint + functions
└─ studio/                        ← the Sanity STUDIO app
   ├─ sanity.config.ts
   ├─ sanity.cli.ts               ← typegen paths point to ../../csendhaboritas
   ├─ schemaTypes/                ← document schemas (band, event, activity)
   ├─ actions/                    ← custom document actions
   ├─ schema.json                 ← generated by `sanity schema extract`
   └─ package.json                ← ONLY studio deps
```

The **frontend** (Next.js) is a SEPARATE repo: `../csendhaboritas`. It keeps its
own copy of the schemas in `src/sanity/schemas/`. When you add or change a
document type, update BOTH repos.

## The #1 gotcha: Blueprint must NOT be co-located with the Studio

`sanity.blueprint.ts` and the Studio's `sanity.config.ts` must live in DIFFERENT
folders. If they sit together, `blueprints deploy` fails with:

> Blueprint should not be co-located with a Sanity Studio.

That is why the Studio lives in `./studio/` while the manifest stays at the root.
Do not move `sanity.config.ts` back up to the root, and do not move
`sanity.blueprint.ts` down into `studio/`.

## Deploying — two DIFFERENT commands, don't confuse them

| What you changed            | Command                          | Run from   |
| --------------------------- | -------------------------------- | ---------- |
| Studio UI / schemas         | `npm run deploy` (`sanity deploy`) | `studio/`  |
| Blueprint / Functions       | `npm run blueprints:deploy`      | repo root  |

- `sanity deploy` deploys ONLY the Studio web app. It does NOT touch Functions.
- Editing `sanity.blueprint.ts` or `functions/**` has NO effect until you run
  `blueprints:deploy` (which is `npx sanity@latest blueprints deploy`).
- The blueprint stack binding lives in `.sanity/blueprint.config.json`
  (stackId `ST-g28hzv2nfe`, project `ce4wb46n`). It is gitignored and stays next
  to the manifest — keep them together so the binding is preserved.
- The root has no `sanity` dependency on purpose; blueprint scripts use
  `npx sanity@latest` so the latest CLI is always used.

## The webhook chain (why a build fires)

1. A document is created/updated/deleted in the Studio.
2. The Blueprint's `vercel-deploy` document function fires — but ONLY for the
   `_type`s listed in the `filter` in `sanity.blueprint.ts`.
   **Gotcha:** a new document type will NOT trigger anything until you add it to
   that filter AND redeploy the blueprint.
3. The function calls the frontend's `/api/revalidate` endpoint (on-demand
   revalidation) and hits the Vercel deploy hook (full rebuild).

Current filter includes: `band`, `event`, `activity`.

## Dependency rules

- Studio deps go in `studio/package.json`. Blueprint/function deps go in the root
  `package.json`. They are separate installs with separate lockfiles.
- The `vercel-deploy` function has no `package.json` of its own, so it resolves
  its imports (`@sanity/functions`) from the ROOT `package.json`. If you add a
  new import to a function, declare it in the root `package.json`.
- Functions run on Node in a sandbox: no native modules (`sharp`,
  `better-sqlite3`, anything with a `.node` binary). Asset cap is 200 MB.

## TypeGen

`studio/sanity.cli.ts` runs typegen and writes the generated types INTO the
frontend repo (`../../csendhaboritas/sanity.types.ts`). Run `npm run typegen`
from `studio/`. If you move files, re-check those relative paths.

## Content model: per-event scoping

`band` and `activity` each hold a required `event` reference (see
`schemaTypes/eventScope.ts`). A band/activity belongs to ONE event — it is a
per-event record, not a singleton. Next year you create NEW band/activity docs
for the new event; previous years stay linked to their event and are preserved.

- New docs auto-attach to the active event via `eventReferenceField`'s
  async `initialValue` (reads the active event with a public read client).
- Band `slug` is unique PER EVENT (custom `isUnique`), so a returning band can
  reuse its slug next year.
- Studio structure (`sanity.config.ts`) shows "aktív esemény" lists (filtered by
  `event->isActive == true`) plus an "Archívum" grouped by event, so old years
  don't clutter the working lists.
- Frontend queries scope everything to the active event via a GROQ subquery:
  `event._ref == *[_type=="event" && isActive==true][0]._id`.
- One-time backfill for pre-existing docs: `scripts/backfill-event.ts`, run with
  `npx sanity exec scripts/backfill-event.ts --with-user-token` from `studio/`.
